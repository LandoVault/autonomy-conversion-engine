# ACE Interview Record — Template

*Template — the operator's own answers are not included in the public release.*

## Purpose and boundary

This record summarizes five diagnostic interview prompts used to identify ACE design requirements. It is not a psychological or clinical assessment. Interpretations remain hypotheses that can be revised by evidence.

Included: the operator's professional, research, project, and workflow behavior.

Excluded: other people's private personal matters (third-party content).

Each prompt below lists its question method (where recorded) and the generic design requirement ACE adopts for the area the prompt probes. These are design rules, not a record of any answer.

## Prompt 1 - limiting belief

### Question method

Ask one question at a time until the most limiting belief is identified, challenge the conclusion, then explain the reasoning.

### Design use (generic)

ACE answers blocking beliefs with structure rather than persuasion. Foundational structure: every deferred item has a reliable return path — return contracts, containment acknowledgments, scheduled resurfacing, closure evidence, and protected blocks.

## Prompt 2 - repeated choices and contradictions

### Design use (generic)

ACE stores possibilities without promoting them to active projects, using WIP limits, evidence gates, decision locks, handoff, and closure.

## Prompt 3 - external-observer view

### Design use (generic)

ACE preserves exploration while forcing conversion into bounded artifacts and evidence.

## Prompt 4 - long-horizon trajectory

### Design levers (generic)

1. two-project work-in-progress limit;
2. one twelve-month compounding anchor asset;
3. one-line return contract;
4. one irreversible evidence unit each week;
5. no redesign without a predetermined observed trigger.

### Design use (generic)

ACE tracks generic reliability and conversion separately, measuring evidence, resumption, handoff, reuse, and autonomy - not only task completion.

## Prompt 5 - avoided questions

### Question method

Identify the strategic questions the system design depends on that have not yet been asked, and record them as open strategic questions.

### Design use (generic)

*(Restored v1.1 — present only in the interview docx.)* "Real handoff state, dual scoreboards, and visible coordination cost without labeling all coordination waste." *(v1.1 editorial gloss, not in the docx: "dual scoreboards" = P0-A reliability and P0-B conversion measured and displayed separately.)*

## Cross-interview synthesis

Work must become:

1. capturable;
2. returnable;
3. resumable;
4. shippable;
5. transferable;
6. auditable;
7. compoundable;
8. bounded.

The final architecture therefore uses Cowork panels for active cognitive work, deterministic loops for continuity, Obsidian for durable human control, and a minimal clinical layer with reviewed passing packages.

## Design hypotheses (generic)

*(v1.1: Test implication column restored from the interview docx — it existed nowhere in markdown.)*

| # | Hypothesis | Test implication |
|---|---|---|
| H1 | Reliable return paths reduce interruption by high-salience items. | Measure whether high-salience items can be deferred without loss. |
| H2 | Explicit ownership, provenance, retained role, and rescue thresholds will make handoffs durable. | Observe successor independence and rescue re-entry. |
| H3 | Separating project motion from operator-created evidence changes portfolio choices. | Compare coordination and evidence reports over 30–90 days. |
| H4 | Generic productivity and frontier conversion must remain co-equal. | Require both scoreboards to pass. |
| H5 | Partial-access design and explicit workspace maps will outperform assumptions of universal agent context. | Seed missing-source cases and test false-completeness behavior. |

These are system-design hypotheses: review them against real-use evidence, and do not load them as standing assumptions into every session.
