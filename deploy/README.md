# Deploying ACE with local storage

This folder deploys ACE on one Windows machine: the engine in this repo, plus three **empty** local stores. It never copies state or content from another ACE deployment. Moving an existing deployment is a separate procedure (see the end of this file).

**Two ways to run it**

- **By hand** — follow the quick start below.
- **By an agent** — hand [`DEPLOY_PACKET.md`](DEPLOY_PACKET.md) to a Cowork panel or a Claude Code session opened at the repo root, with the instruction *"Execute deploy/DEPLOY_PACKET.md"*. The packet follows ACE's own session-packet format. The agent stops for the owner's decisions and ends by writing an exit package.

## What gets deployed

| Store | Variable | Role | Git | Remote |
|---|---|---|---|---|
| this repo | — | spec, engine, tests, deploy scripts | yes | your choice (code only; holds no instance state) |
| control plane | `ACE_STORE` | state, audit log, outbox / pending / archive, packets, metadata | yes | optional — **PRIVATE only** |
| content plane | `ACE_LOCAL` | personal / IP content: captures, research, artifacts | yes | **never** (hard rule) |
| hub vault | `ACE_HUB` | Obsidian vault: projects, commitments, evidence, generated views | yes | none (local) |

The layout and the binding writer matrix are in `spec/11_STORAGE_AND_FILING.md`. The operating contract every agent follows is `CLAUDE.md`.

**`CLAUDE.md` is written for its original owner.** A different owner adapts its owner-specific lines before first use (name, scope exclusions, identifier aliases). The hard rules stay in force:

- no PHI or credentials in any store;
- the two-plane split;
- never delete — supersede-by-move;
- models propose, code records, the owner approves.

## Prerequisites

- Windows 10/11, PowerShell 5+.
- Python ≥ 3.9 (stdlib only — no packages to install).
- Git ≥ 2.28.
- Obsidian, to view the hub (optional).
- Three folders on **local** disks, separate and not nested.
- A **local or offline** backup destination (spec/11: no cloud-touching backup without an explicit ruling).

## Quick start

```powershell
# 1. clone the repo and open a terminal at its root
# 2. choose the store folders — copy and edit the example, run it once, open a NEW terminal
.\deploy\ace_env.example.ps1
# 3. see the plan, then create the stores (never overwrites or deletes)
python deploy\bootstrap_stores.py
python deploy\bootstrap_stores.py --apply
# 4. verify (layout, write probes, no content-plane remote, private control-plane remote, engine paths, tests)
python deploy\verify_deploy.py
# 5. schedule the daily backup (the only loop a fresh deployment schedules)
.\deploy\register_backup_task.ps1 -BackupDest 'E:\ACE_backup'
# 6. open the hub folder as an Obsidian vault
```

Unset variables fall back to the reference deployment's paths: `F:\git\ACE_storage`, `F:\ACE_local`, `F:\ACE_hub`, backup `G:\ACE_backup`. The engine, the loops, the backup script and both deploy scripts all read the same variables.

## Initializing the hub (ACE_HUB)

`bootstrap_stores.py --apply` initializes the hub in one pass. It creates only what is missing:

| What | Detail |
|---|---|
| Folders | `inbox/`, `projects/`, `commitments/`, `evidence/`, `views/` |
| `README.md` | the surfaces, the capture and review marks, and the rules |
| `.obsidian/app.json` | new notes (Ctrl+N) land in `inbox/` |
| The four views | **generated by the engine**: `Today`, `Pending Panel Updates`, `Commitments and Return`, `Weekly Review` |
| Local git repo | the scaffold is committed as `ACE Loop` |

The views matter. They are the gesture watcher's baseline: a tick or strike counts only as an edit against an engine-written view.

Then:

1. **Open it.** In Obsidian, choose *Open folder as vault* and pick the hub folder. No community plugins are needed — none is allowed in the first slice (spec/03 §6).
2. **Capture.** Ctrl+N, free text, one thought per note. Marks: `@YYYY-MM-DD` return date · `@name` person · `@call` `@read` `@desk` `@msg` · hedge words send the note to the idea queue.
3. **Review.** In `views/Pending Panel Updates.md`: tick = accept, `~~strike~~` = reject, `@YYYY-MM-DD` = defer. Then run `python engine\gesture_watcher.py`.
4. **Regenerate views** any time with `python engine\ace_engine.py views`. Harvest pending ticks first, because regeneration overwrites the views.
5. **Cross-device (optional).** The owner enables Obsidian Sync in-app with their own account. Agents never touch credentials. The hub never gets a git remote.

**An existing vault without these pieces** (for example, created by hand) needs nothing re-created: `bootstrap_stores.py --apply` adds only the missing items. Either way, `verify_deploy.py` reports *hub views generated* and *Obsidian new notes land in inbox/*.

## Not part of deployment — owner decisions

| Item | Why it's excluded |
|---|---|
| Activating `ace tick` (the scheduled deterministic loop) | Ruling R5-2 in `spec/10_OPEN_QUESTIONS.md`; not built yet |
| Running the gesture watcher or clarify loop on a schedule | Same gate |
| A git remote for the control plane | Allowed only if private. `verify_deploy.py` checks visibility when `gh` is installed |
| Any clinical layer (ACE-C) | Institution-side by design; never in these stores |

## Daily use after deployment

| Step | Command |
|---|---|
| A panel writes an exit package | to `$ACE_STORE\outbox\X-<id>\EXIT_PACKAGE.json` |
| Validate it | `python engine\ace_engine.py validate X-<id>` → `pending/` + hub Pending view |
| Accept or reject | `python engine\ace_engine.py accept X-<id>` / `reject X-<id>`, or tick/strike it in the hub view and run `engine\gesture_watcher.py` |
| Regenerate views | `python engine\ace_engine.py views` |
| Undo | `python engine\ace_engine.py rollback <event-id>` (newest-first; recorded as a new audited transition) |

## Moving an existing deployment to a new machine

Do **not** bootstrap empty stores over the top of a move. Restore instead:

1. Restore from the latest backup bundles: `git clone <dest>\bundles\ACE_storage_<date>.bundle ACE_storage`, and the same for `ACE_local` and `ACE_hub`.
2. Mirror the latest robocopy folders on top, for files not yet committed.
3. Set the three variables to the new paths and run `python deploy\verify_deploy.py`.
4. Re-register the backup task.
5. Re-add the control-plane remote (private) if you had one. **Never** add one to the content plane.

## Troubleshooting

| Symptom | Fix |
|---|---|
| `PermissionError` on rename | A transient antivirus/indexer lock. The engine retries up to ~1.5 s. If it persists, exclude the store folders from real-time indexing |
| `REFUSED: … unfinished` | A previous accept crashed midway. Re-run the same `accept X-<id>` to finish it |
| `verify` FAIL on the content-plane remote | Remove that remote (`git -C <ACE_LOCAL> remote remove origin`); personal content never leaves the machine |
